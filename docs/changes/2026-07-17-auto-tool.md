## Problem Statement

玩家目前只能同時進行「一個手動行動」。需求：新增主介面按鈕「自動工具」，讓玩家在手動行動之外，額外掛載最多 3 個「自動工具」並行運作。四種工具（採集/建設/戰鬥/研究）每一種在任一時刻只能處於三種狀態之一：手動行動、自動工具、閒置。

規則：
- 只能挑選目前閒置的工具（既非手動行動，也非其他自動工具）開成自動工具。
- 下拉選 1~6 個「該工具專屬素材」啟動（不可用萬能素材替代）；每 1 個素材 = 1 小時運行時間。
- 運行中效果等同玩家行動：各自獨立的結算週期計時，各自依 action-resolver 計算效率、素材掉落、產出分配、資源消耗、關卡進度與試煉貢獻。
- 互斥（雙向）：正在自動運行的工具不能被選為手動行動；手動行動的工具不能再開成自動工具；同一工具不能同時有兩個自動工具。

## Recommended Direction

方向 A（採用）：新增 `player_auto_tools` 表，一列代表一個運行中的自動工具（主鍵 `user_id + tool_type`），各自帶 `completion_time`（下次結算）與 `expires_at`（到期時間）。cycle-engine 的 Watcher tick 與「開啟介面 / Refresh」補算流程，除了掃 `players.completion_time`，也掃這張表逐一結算；結算直接複用 action-resolver（以該列的 `tool_type` + `action_target` 為輸入，產出/素材/進度歸於該 `user_id`）。新增 `auto_tool_manager` 管理啟動、延長、查詢、結算、到期與互斥約束。

此方向與現有 `trial-manager`「獨立並行子系統 + Watcher tick」的先例一致，不動既有單一行動模型，變更面可控。

### 排除的替代方案

- 方向 B：在 `players` 表加 4 組 per-tool 計時欄位（8+ 欄）。正規化差、Watcher 查詢變醜、不易擴充，否決。
- 方向 C：把手動行動與自動工具統一成單一「行動流」抽象表。理論優雅但需大改 cycle-engine 與既有穩定模型，違反最小變更原則，否決。

## MVP Scope / Not Doing

範圍內：
- 新增 `player_auto_tools` 表（DB schema）。
- 新增 `auto_tool_manager`：啟動（扣素材、寫入計時）、延長（疊加素材）、查詢、單一自動工具結算、到期結束、互斥約束。
- cycle-engine：Watcher tick 與開啟介面補算流程納入自動工具結算。
- action-resolver：支援以「指定 tool_type + action_target + user_id」進行單週期結算（供自動工具複用），不再僅從 `players.action` 讀取。
- player-manager：`set_action` 新增互斥守衛（拒絕選中正在自動運行的工具）。
- UI：主介面新增「⚙️ 自動工具」按鈕與其子介面（顯示運行中自動工具與剩餘時間、選工具、選建設目標、選素材數量 1~6、確認）；行動下拉/確認需反映互斥。
- 新增環境變數：`AUTO_TOOL_SECONDS_PER_MATERIAL`、`AUTO_TOOL_MAX_MATERIALS`。
- 文件更新：db-schema、cycle-engine、action-resolver、player-manager、formula（env）、ui-renderer、command-handler，以及新增 `managers/auto-tool-manager.md`。

範圍外：
- 自動工具不消耗 AP（啟動成本是素材，非 AP）；瞬間行動（burst）仍只作用於手動行動。
- 萬能素材不可用於啟動自動工具（明確排除）。
- 自動工具的公開通知（開始/結束）：不新增公開通知類型；結算過程沿用既有事件（關卡通關、建築升級、試煉成功等）。
- 到期不做最終半週期結算（比照現有「只有換行動才做 partial」）。

## Key Assumptions

- 「效果等同玩家行動」= 每完整週期跑一次 action-resolver：扣村莊資源（×0.5 懲罰同規則）、產出分配、素材掉落（stage-matching 加倍規則）、關卡進度、試煉貢獻、建築升級判定、通知，全部歸於該玩家。
- 到期判定：只結算 `completion_time <= min(now, expires_at)` 的完整週期；`now >= expires_at` 時結束該自動工具（刪除該列，釋放該工具），進行中的未完成週期丟棄，不做 partial。
- 素材掉落若掉到該工具自身素材，可再投入延長同一自動工具（正回饋循環為預期行為）。
- 延長上限固定 6 小時，補充規則見架構決策 #5（已確認）。

## Architecture Decisions

1. 新增 `player_auto_tools` 表，主鍵 `(user_id, tool_type)`，天然保證「同一工具不能兩個自動工具」。欄位：`action_target`（建設用，其餘 null）、`completion_time`、`last_update_time`、`expires_at`、`started_at`、`updated_at`。新增 `idx_auto_tools_completion` 供 Watcher 掃描。整張新表由 `CREATE TABLE IF NOT EXISTS` 建立，既有 DB 於 `init_db()` 自動補建，不需 ALTER 遷移。

2. 結算複用 action-resolver。action-resolver 現在從玩家行動設定取輸入；改為可接受明確的 `(tool_type, action_target, user_id)`，使手動行動與自動工具走同一結算路徑。手動行動呼叫端維持既有語意（以 `players.action` 為輸入）。

3. cycle-engine 的 Watcher tick 與「開啟介面 / Refresh」補算，除既有玩家行動補算外，新增掃描 `player_auto_tools`：對每列 while-loop 補算 `completion_time <= min(now, expires_at)` 的完整週期（受 `MAX_CYCLES_PER_SETTLEMENT` 限制），到期則結束。自動工具的 `cycle_time_reduce` 詞條以該工具自身詞條計算，與手動行動獨立。

4. 互斥約束的唯一真實來源在 `auto_tool_manager` 與 `player_manager.set_action`：
   - 啟動自動工具 T：T ≠ 玩家當前 `action` 且 T 不在 `player_auto_tools`；素材 `materials[T] >= 數量`（不吃萬能）。
   - 設定手動行動 T：T 不在 `player_auto_tools`（新增守衛）。
   UI 僅作即時提示/disabled，最終仍以後端守衛為準（防併發競態）。

5. 延長（refuel）與上限：任一時刻單一自動工具剩餘運行時間上限固定 6 小時（= `AUTO_TOOL_MAX_MATERIALS × AUTO_TOOL_SECONDS_PER_MATERIAL`）。素材以整數小時計，可補充數量 `max_add = floor((CAP_SECONDS - remaining_seconds) / AUTO_TOOL_SECONDS_PER_MATERIAL)`；`remaining_seconds = max(0, expires_at - now)`。
   - 補充僅在 `max_add >= 1` 時開放（等價於「剩餘時間已較上限減少滿 1 小時」）；下拉提供 `1..max_add`。投入 X 後 `expires_at += X × AUTO_TOOL_SECONDS_PER_MATERIAL`，因 `X <= max_add` 故必不超過 6 小時上限。
   - 首次啟動時 `remaining = 0`，`max_add = 6`，下拉提供 1~6。
   - 例：剩餘 5:01 → `max_add = floor(59min/60min) = 0` → 補充 disabled；剩餘 0:01 → `max_add = floor(359min/60min) = 5` → 最多補 5 個成為 5:01。
   - 後端啟動/補充皆再驗證 `X <= max_add`（防 UI 過期或併發競態）。

6. 自動工具不消耗 AP。素材成本只扣該工具自身素材，無萬能素材 fallback（與 gear/affix 的萬能素材規則刻意不同）。
